# 322. Coin Change

**Сложность:** Medium

**Ссылка:** https://leetcode.com/problems/coin-change/

## Условие

Даны номиналы монет `coins` и сумма `amount`. Вернуть **минимальное число монет**, которыми набирается эта сумма. Монет каждого номинала неограниченно. Если сумму набрать нельзя — вернуть `-1`.

## Примеры

```
coins = [1,2,5],  amount = 11  → 3    (5 + 5 + 1)
coins = [2],      amount = 3   → -1
coins = [1],      amount = 0   → 0
coins = [1,3,4],  amount = 6   → 2    (3 + 3)
```

Последний пример — контрпример жадности: «бери самую крупную» даёт `4+1+1`, три монеты, а оптимум `3+3`.

## Ограничения

- `1 <= coins.length <= 12`
- `1 <= coins[i] <= 2^31 - 1`
- `0 <= amount <= 10^4`

## Решения

Оба подхода — один комплект, отличается направление счёта.

| шаг | |
|---|---|
| **состояние** | `f(x)` — минимальное число монет для суммы `x` |
| **переход** | `f(x) = 1 + min( f(x - c) )` по всем `c` из `coins`, где `c <= x` |
| **база** | `f(0) = 0`, остальные ячейки — `Infinity` |
| **ответ** | `f(amount)`, с переводом `Infinity` → `-1` |

Три вещи здесь появляются впервые за серию DP-задач.

**Переход перебирает набор, а не два варианта.** В лестницах и грабителе кучек всегда было ровно две. Здесь их столько, сколько номиналов, и внутри перехода стоит цикл.

**Из-за этого впервые работает формула «сложность = число состояний × стоимость перехода»:** `O(amount)` состояний на `O(coins.length)` перехода даёт `O(amount · coins.length)`. В первых трёх задачах переход стоил `O(1)` и множитель был невидим.

**Состояние индексируется не позицией во входном массиве, а суммой.** Монеты неограничены и переиспользуемы, поэтому позиция в `coins` не описывает никакого прогресса. Размер таблицы — `amount + 1`, к длине `coins` отношения не имеет.

### Решение 1 — таблица снизу вверх (`tabulation.ts`)

С неё начали. Заполняем `x` от `1` до `amount`, для каждой суммы перебираем номиналы.

- **Сложность:** время `O(amount · coins.length)`, память `O(amount)`.
- Стек не расходует, берёт **любой** допустимый вход.

### Решение 2 — мемоизация сверху вниз (`memo.ts`)

Та же рекуррента, спуск от `amount` к базе.

- **Сложность:** та же, плюс глубина стека `O(amount / min(coins))`.
- **Не выдерживает максимальный вход.**

## Сложность

| подход | время | память | предельный вход |
|---|---|---|---|
| `tabulation` | `O(amount · coins.length)` | `O(amount)` | любой |
| `memo` | `O(amount · coins.length)` | `O(amount)` + стек `O(amount / min(coins))` | до `amount ≈ 5000` при `coins = [1]` |

## Заметки

- **Первая задача серии, где выбор направления — вопрос работоспособности, а не вкуса.** Глубина рекурсии равна `amount / минимальный номинал`. При `coins = [1]` и `amount = 10^4` это десять тысяч кадров, и Node падает с `RangeError: Maximum call stack size exceeded`. Замеренный предел — около `amount = 5000`, вдвое ниже границы условия. Поэтому кейс с максимальной глубиной помечен `skipFor: ["memo"]`: это не баг реализации, а свойство подхода.
- **Порядок перебора монет влияет на глубину.** Если идти по убыванию номиналов, первый спуск делает крупные шаги, глубина падает до `amount / максимальный номинал`, и к возврату кэш уже прогрет — `[1,2,5]` на `10^4` после этого проходит. Но `coins = [1]` не спасает ничто. Сортировку не добавляли намеренно: она расширяет область применимости, не закрывая её, и создаёт иллюзию, будто проблема решена.
- **Маркер «недостижимо» должен проигрывать операции склейки.** Здесь склейка через `min`, поэтому маркер — `+Infinity`: он никогда не выиграет у настоящего ответа, а `1 + Infinity` остаётся `Infinity`, и недостижимость сама течёт по таблице без единой проверки. Значение `-1` на этом месте всё сломало бы: `Math.min(-1, 2)` равно `-1`, маркер победил бы верный ответ. Общее правило: для `min` — `+Infinity`, для `max` — `-Infinity`, для подсчёта вариантов — `0`. Перевод во внешний формат делается один раз на выходе, а не размазывается по таблице.
- **Условие `c <= x` — не оптимизация, а защита.** Без него в табуляции читается отрицательный индекс, получается `NaN`, и `Math.min(NaN, …)` разносит порчу по всем зависимым ячейкам. В мемоизации хуже: спуск в отрицательные суммы бесконечен и кончается падением. Один и тот же пропуск даёт разные отказы в двух подходах — поэтому тест на монету больше суммы сторожит оба.
- **Проверка кэша только по наличию ключа.** База здесь `f(0) = 0`, а ноль falsy: с `if (cache[x])` нулевая ячейка не читается, и запись после цикла затирает её значением `Infinity + 1`. Дальше `Infinity` растекается вверх, и любой вход возвращает `-1` — правдоподобный, предусмотренный условием ответ, который легко принять за правильный.
